# 请求插件规则化 - 产品文档

> 修订 v2（2026-11-24）：按 #40 评审意见与 Operator 决策修订，修订说明见 [revision_notes.md](./revision_notes.md)。

## 目标

网关目前内置了三个请求改写功能（强制改写 CCH、屏蔽 Claude Code 跟踪、Responses API 粘性路由），但只能通过「高级设置 → 请求处理」里的全局开关一刀切地开启或关闭，无法针对特定用户、模型或渠道灵活控制。

本迭代将请求改写底层统一升级为**插件规则**，同时兼顾“全局快捷开关”与“按条件精细管控”两种使用方式：
- **保留高级设置快捷开关，自动联动系统规则**：继续保留「高级设置 → 请求处理」下的三个开关，开启或关闭设置时，系统自动创建并启用/禁用对应的**系统规则**。
- **系统规则与用户规则分层**：由系统设置生成的规则属于**系统规则**，在规则列表中只读展示，不允许用户在规则页直接修改（包括启用/禁用）或删除；管理员也可以在「规则管理」中自行创建**用户规则**，按用户、模型、供应商组合条件启用插件并自定义参数。

## 功能特性

### 1. 系统规则与用户规则

规则分为两类，每条规则具有唯一的业务来源标识：

| 类别 | 来源 | 规则管理页允许的操作 | 说明 |
|---|---|---|---|
| **系统规则** | 由「高级设置 → 请求处理」开关自动创建与联动 | **完全只读**（不允许在规则页启用/禁用、编辑或删除） | 承载网关全局请求处理开关对应的默认规则，启停统一在「高级设置」中操作 |
| **用户规则** | 管理员在「规则管理」手动创建 | 新建、编辑、启用 / 禁用、删除 | 按业务需要针对特定用户、模型、供应商定制限流、访问控制或请求插件规则 |

- 「规则管理」页面分为**「用户规则」**和**「系统规则」**两部分展示：
  - **用户规则**：展示管理员创建的规则，支持新建、编辑、启用/禁用和删除。
  - **系统规则**：独立区域只读展示系统规则及其当前启用状态（无编辑/删除操作，状态开关只读）。提示文案：
    - 主租户视图：「系统规则请前往『高级设置 → 请求处理』中开启或关闭」；
    - 非主租户视图：「系统规则由系统管理员在主租户统一配置」（非主租户无权修改高级设置）。
- 当管理员需要精细化控制某个插件（例如仅对指定用户组改写 CCH，或为不同用户组配置不同的 CCH 值）时，推荐在「高级设置 → 请求处理」中关闭全局开关（对应系统规则随之禁用），再在「规则管理 → 用户规则」中创建所需的用户规则。若不关闭全局开关，系统规则与用户规则会**依次全部执行**（见 §3「多规则执行顺序」）。

### 2. 高级设置「请求处理」联动规则

「高级设置 → 请求处理」保留以下三个设置项，并与对应的系统规则联动：

| 设置项名称 | 联动行为 | 对应内置插件说明 | 可选参数（用户规则可配） |
|---|---|---|---|
| **强制改写 CCH** | 开启设置即自动创建/启用对应系统规则；关闭设置即禁用该系统规则 | 将 Anthropic 系统提示词开头的 `cch=xxx;` 改写为指定值 | `cchValue`（默认 `A1234`） |
| **屏蔽 Claude Code 跟踪** | 同上 | 规范化 Claude Code 在系统提示词中注入的日期追踪标记，避免破坏缓存命中 | 无 |
| **Responses API 粘性路由** | 同上 | 当 Responses 请求未携带 `prompt_cache_key` 时，自动注入缓存 Key 提升缓存命中率 | 无 |

- **生效时效**：保存后在当前网关实例立即生效；多实例部署（如 Cloudflare Workers 多 isolate）下其他实例最迟 60 秒内生效。
- **「屏蔽 Claude Code 跟踪」开关修复**：旧版本中该开关的前端保存字段与后端读取字段不一致，导致在界面上关闭后实际仍处于开启状态。本迭代统一为后端字段，升级时以管理员在界面上最后保存的值为准（详见技术文档 §6.2）。升级后，曾在界面上关闭过该开关的部署将**真正变为关闭**。

### 3. 规则管理新增「请求插件」类型

在「规则管理」原有的「频率限制」和「访问控制」基础上，新增**「请求插件」**规则类型：
- **匹配条件**：与现有规则完全一致，支持「所有请求（全局）」或按**用户 / 模型 / 供应商**组合条件匹配。
- **插件选择与参数**：下拉选择要启用的内置插件；插件参数以 **JSON 文本**填写（选填，留空视为 `{}`），不提供按字段的表单。保存时后端校验 JSON 格式及插件参数是否合法（如 `cchValue` 的字符集与长度），不合法时提示具体原因并拒绝保存。
  - 示例：强制改写 CCH 填 `{"cchValue": "B5678"}`；无参数插件留空或填 `{}`。
- **多规则独立生效**：同一个插件可以创建多条用户规则（例如：规则 A 对用户组 1 将 CCH 改写为 `A1234`，规则 B 对用户组 2 改写为 `B5678`）。
- **多规则执行顺序**：一次请求同时命中多条插件规则（包括系统规则与用户规则同时命中同一插件）时，**全部依次执行**：
  - 先按插件优先级从小到大执行；同一插件（优先级相同）的多条规则按规则 ID **从小到大**执行；
  - 后执行的规则作用在前一条规则的结果之上。例如系统规则（ID 小）先把 CCH 改为 `A1234`，用户规则（ID 大）再改为 `B5678`，最终发往上游的是 `B5678`；而粘性路由在前一条规则已注入缓存 Key 后，后续规则检测到已有 Key 将不再改动。
- **对所有请求生效**：插件用于协议兼容与缓存优化，对管理员（含 root）和普通用户的请求一视同仁生效；「模型路由测试」中的请求同样会执行插件（与现状一致）。

### 4. 执行与容错体验

- **跨协议自动适配**：无论客户端与上游是同协议直通，还是经过网关自动协议转换（如 Claude Code 调 Responses 渠道），插件都会在正确的协议阶段自动生效。
- **失败切换时逐次匹配**：请求因上游失败切换到其他供应商时，每次尝试会按该次实际路由到的供应商重新匹配插件规则。
- **异常不阻断请求**：插件执行出错或配置不当时，仅在请求详情的时间线中记录告警，请求照常发往上游，不会导致调用失败。
- **安全保护**：插件允许修改请求体与普通请求头，但不能整体替换请求体、不能修改模型/流式相关字段、不能覆盖上游鉴权信息或网关管控的请求头，从而不破坏鉴权与流式计费统计。
- **时间线留痕**：只有当插件真正修改了当前请求时，才会在「请求记录 → 详情时间线」中展示插件执行记录（记录生效的插件、规则与修改位置，不记录请求内容原文）；未发生修改时不产生冗余记录。升级前产生的历史插件记录保持原样可正常查看。

## 产品边界（非目标）

- **不支持用户自定义上传插件代码**：插件由系统内置随版本提供，不支持在后台编写或上传脚本。
- **不改写上游响应内容**：插件仅在请求发往上游前生效，不对上游返回的响应做改写。
- **规则条件不匹配请求体内容**：规则条件仅限用户、模型、供应商三个管理维度；请求内容是否需要改写（如是否包含特定提示词标记）由插件自身自动识别。
- **不新增规则级优先级字段**：执行顺序由插件内置优先级 + 规则 ID 决定。
- **插件参数不提供字段化表单**：仅 JSON 文本输入 + 后端校验。

## 验收标准

- [ ] 升级后自动生成三条预置「系统规则」，状态与升级前管理员在「高级设置 → 请求处理」中最后保存的三个开关一致（含「屏蔽 Claude Code 跟踪」旧字段兼容）
- [ ] 在「高级设置 → 请求处理」中开启或关闭三个开关时，自动定位并创建/更新对应系统规则的启用状态，当前实例立即生效
- [ ] 「屏蔽 Claude Code 跟踪」开关在界面关闭后，请求不再被改写（修复旧版不生效问题）
- [ ] 系统规则在「规则管理」中完全只读：无法通过规则管理页或规则接口修改（含启用/禁用）或删除
- [ ] 规则管理页分「用户规则 / 系统规则」两区展示；非主租户视图下系统规则提示文案正确
- [ ] 管理员可在「规则管理」中新建、编辑、启停、删除「请求插件」类型的用户规则，按用户、模型、供应商条件触发改写
- [ ] 插件参数以 JSON 填写；非法 JSON、非对象、未知参数或参数值不合法（如 `cchValue` 含非法字符）时保存被拒并提示原因
- [ ] 为「强制改写 CCH」用户规则配置自定义 `cchValue` 时，按配置值生效；系统规则与用户规则同时命中时按「规则 ID 从小到大依次执行、后者覆盖前者结果」生效
- [ ] 同协议直通与跨协议转换场景下，对应协议的插件均能正确生效
- [ ] 插件实际修改了请求时，请求详情时间线可见插件记录；未发生修改时不留空记录；历史插件记录正常显示
