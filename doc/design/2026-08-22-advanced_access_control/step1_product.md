# 网关请求规则（规则化：限流 + 访问控制）- 产品文档

## 目标

当前网关对 `/llm/v1/chat/completions`、`/llm/v1/messages`、`/llm/v1/responses` 三个 LLM 入口没有任何速率/用量限制，也没有模型访问控制——任意用户、任意模型都可无限调用，缺少对上游成本与资源占用的保护手段，也无法满足「某模型只能由特定用户使用」这类组织管控诉求。

本迭代引入**规则化（rule）**能力：一条规则 = 匹配条件（`scope`）+ 动作参数（`config`）+ 类型标识（`type`），统一承载两类能力：

- **限流（rate_limit）**：按用户 / 模型 / 供应商等条件组合配置 **RPM（每分钟请求数）** 上限，超限请求返回 429 拒绝。
- **访问控制（access_control）**：按用户 / 模型 / 供应商等条件组合配置**访问限制**，例如「某模型仅某些用户可访问」，命中即返回 403 拒绝。

其中 `scope` 是**布尔表达式树**——多个条件可用 AND / OR 自由组合、嵌套，统一表达两类规则的匹配逻辑。

## 功能特性

### 规则化配置

- 新增 `rule` 规则表，一条规则由三要素组成：
    - **type**：规则类型标识（本迭代内置 `rate_limit`、`access_control`），用于分派到对应处理器，避免从 JSON 内容反向推断类型。
    - **scope**：匹配条件（JSON），是一棵**布尔表达式树**（叶子条件用 AND / OR 组合，见「条件与表达式树」）。
    - **config**：该类型规则的参数（JSON）。`rate_limit` 类型下为 `{ rpm }`；`access_control` 类型无需参数（保留空 `{}`，树命中即拒绝）。
- 规则支持启用/禁用（`enabled`），无需删除即可临时关停。

### 条件与表达式树（scope）

**统一节点结构**：所有节点都由 `type`、`oper`（可选）、`values` 三个 key 组成，叶子条件与逻辑节点形态统一：

- `type`：节点类型。叶子为判断维度（`user_id` / `model_id` / `vendor_id`）；组合为 `and` / `or`；恒真为 `const`。注意与规则顶层 `type`（规则类型 `rate_limit` / `access_control`）区分。
- `oper`：运算符，仅叶子节点携带。
- `values`：统一取值列表。叶子为比较值（number[]）；`and` / `or` 为子节点列表（非空）；`const` 为 `[true]`。

**叶子条件**：对单一维度的一次判断：

| key | 取值 | 说明 |
|-----|------|------|
| `type` | `user_id` / `model_id` / `vendor_id` | 判断的维度 |
| `oper` | `=` / `!=` / `in` / `not in` | 运算符 |
| `values` | `=`/`!=` 为单元素 number[]；`in`/`not in` 为非空 number[] | 比较值列表 |

**表达式树**：`and`（全部满足）/ `or`（任一满足）通过 `type` 标识，子节点放在 `values` 中，可任意嵌套：

```jsonc
// 单条件（叶子）
{ "type": "model_id", "oper": "=", "values": [5] }

// AND：模型 5 且用户 3
{ "type": "and", "values": [
    { "type": "model_id", "oper": "=", "values": [5] },
    { "type": "user_id",  "oper": "=", "values": [3] }
]}

// OR：模型 5 或 6（共享同一额度 / 同一限制）
{ "type": "or", "values": [
    { "type": "model_id", "oper": "=", "values": [5] },
    { "type": "model_id", "oper": "=", "values": [6] }
]}

// 嵌套：模型 5 且（用户 3/4/5 或 供应商 9）
{ "type": "and", "values": [
    { "type": "model_id", "oper": "=", "values": [5] },
    { "type": "or", "values": [
        { "type": "user_id",   "oper": "in", "values": [3, 4, 5] },
        { "type": "vendor_id", "oper": "=",  "values": [9] }
    ]}
]}
```

**恒真节点（全局兜底）**：`{ "type": "const", "values": [true] }` 恒为真（全命中），用于「对所有请求施加统一限制」的兜底规则。`and` / `or` 节点的 `values` 必须为**非空**数组——空数组不合法（避免歧义）。

**维度语义**：

- `user_id` / `model_id` 为标量维度：`=`/`!=` 为相等/不等，`in`/`not in` 为在/不在数组内。
- `vendor_id`：请求实际路由到的上游供应商 ID，与 `user_id`/`model_id` 一样为标量维度。含 `vendor_id` 条件的规则在**路由选择之后**执行（此时已确定实际使用的供应商），不含 `vendor_id` 的规则在路由选择之前执行。

### 限流（rate_limit）

- 规则命中（`scope` 树求值为真）即对命中请求施加限流。
- **RPM（requests per minute）**：准入时验证 + 记账一步完成——自增计数（先加后判），60s 滑动窗口内请求数**超过上限**即拒绝（`rpm = N` 恰好放行 N 个请求，第 N+1 个拒绝）。
- rpm 取值语义：`null` / 缺省 = **不限制**（规则命中但放行）；`0` = **不可用**（无请求额度，所有命中请求一律 429，可作硬性阻断）；`N（N > 0）` = 滑动窗口内最多 N 个请求。
- **本期仅 RPM**：TPM（token 限流）留待后续版本（`RateLimitStore` 接口已预留扩展位）。
- **供应商级限流与 failover**：命中供应商级限流时视为「该上游繁忙」，failover 开启时切换到其它供应商，全部耗尽 / 关闭时返回 429。
- 常见示例：模型级、模型组（`model_id in [...]`）、供应商级（`vendor_id = 9`）、用户级、用户×模型、全局兜底（`{ "type": "const", "values": [true] }`）。

### 访问控制（access_control）

- **语义**：与限流共用同一棵 `scope` 树——**树命中即拒绝（403）**，无独立的「白名单模式」、无额外 config。
- **白名单写法**：要表达「模型 5 仅用户 3/4/5 可访问」，写「拒绝名单外的用户」即 `not in`：

  ```jsonc
  { "type": "and", "values": [
      { "type": "model_id", "oper": "=", "values": [5] },
      { "type": "user_id",  "oper": "not in", "values": [3, 4, 5] }
  ]}
  ```

- **排除少数**：要表达「除用户 10/11 外均可访问」，写 `in`（拒绝这些用户）：

  ```jsonc
  { "type": "and", "values": [
      { "type": "model_id", "oper": "=", "values": [5] },
      { "type": "user_id",  "oper": "in", "values": [10, 11] }
  ]}
  ```

- **默认放行**：无任何访问控制规则命中时，请求照常放行。访问控制是「按需收紧」而非「默认关闭」，与限流「无规则零回归」的哲学一致。
- **判定语义（fail-closed）**：命中多条访问控制规则时，任一条命中即整体拒绝（deny-wins）。
- **拒绝行为**：树命中 → 返回 **HTTP 403**（区别于限流的 429）。
- **检查时机**：在限流**之前**检查——无权限请求直接 403，不再进入限流计数。
- **root 旁路**：root 用户不受访问控制限制（与限流一致）。

### 规则管理

- 提供规则的增删改查 API（管理员权限），删除/修改后即时生效。
- 前端新增「规则」管理页：规则列表、新增/编辑对话框（名称、启用开关、type、scope **条件树编辑器**、按 type 渲染的 config 表单）。

### 超限 / 拒绝行为

- **限流超限**：返回 **HTTP 429**，携带 `Retry-After` 头（重试建议秒数）。
- **访问拒绝**：返回 **HTTP 403**。
- **失败留痕**：429 / 403 均写入一条失败记录（`failed_code` = `rate_limit_exceeded` / `access_denied`），便于审计与排查（阶段一用 `recordService.recordFailedRequest`，阶段二标记已创建 record）。
- 错误体按请求协议输出 OpenAI / Anthropic / Responses 三套格式（复用现有 `buildLlmErrorResponse`）。

### 执行阶段

规则在请求链路的不同时间点检查，取决于 scope 是否引用「供应商」（`vendor_id`）：

| 阶段 | 时机 | 检查的规则 |
|------|------|-----------|
| **阶段一：路由前** | 鉴权、解析出用户与模型之后，进入路由 / 供应商选择之前 | 不引用供应商的规则（按用户、模型、组合条件、全局兜底） |
| **阶段二：路由后** | 路由选定实际供应商之后、调用上游之前 | 引用供应商的规则（scope 含 `vendor_id`） |
| **阶段三：响应后** | 上游成功响应之后 | 本期无（TPM 记账留待后续） |

执行要点：

- **每条规则只在一个阶段检查**：按 scope 是否引用供应商自动分流，管理员配置时无需关心阶段划分。
- **逐级递进，拒绝即终止**：阶段一 → 阶段二 → 上游调用；任一阶段命中拒绝（403 / 429）即终止，不再进入后续阶段。
- **供应商级限流自动切换**：阶段二命中供应商级限流视为「该上游繁忙」，优先尝试其它可用供应商，全部不可用才返回 429。
- **访问控制先于限流**：同一阶段内先判权限（403）再判限流（429），无权限请求不消耗限流计数。
- **root 用户全程旁路**：不匹配任何规则、不计数。
- **路由测试是纯诊断**：管理员的 `/model/route-test.json`（inspect 模式）跳过规则检查，只走真实 `/llm/v1/*` 流量时规则才生效。

## 产品边界（非目标）

- **本期只做内存限流，且仅 RPM**：计数器存放在进程内存中，限流为「单实例级别」。Cloudflare Workers（多 isolate）、MySQL 多实例部署下无法跨实例精确限额，这是既定取舍，接口已预留，后续可切换为 DB / Durable Object 存储。TPM 限流本期不做。
- **不新增其它规则类型**：并发数、成本配额、TPM 等逻辑仅预留扩展位，不在本期实现。
- **表达式树仅支持 AND / OR**：不做 NOT 节点（叶子级 `!=` / `not in` 已覆盖「取反」需求）；`and` / `or` 的 `values` 必须非空，恒真用显式 `{ "type": "const", "values": [true] }` 节点表达。
- **`/llm/v1/models` 不纳入规则**：模型列表既不做限流，也**不按访问控制过滤**——受限模型对无权限用户仍可见，仅在实际调用时返回 403（本迭代只控制调用，不在列表层隐藏）。
- **root 用户旁路全部规则**（Tauri 桌面自动登录依赖 root token，不能拦截）。
- **路由测试不应用规则**：管理员的 `/model/route-test.json`（inspect 模式）是纯诊断接口，阶段一（绕过 LLM 中间件）与阶段二（inspect 跳过）都不检查，规则只约束真实 `/llm/v1/*` 请求流量。
- **不改变请求链路、路由选择、计费逻辑**：规则不参与路由选路与计费，只是路由前（阶段一）与路由后（阶段二）的两道准入闸门。

## 验收标准

- [ ] 新增 `rule` 表，迁移（`migrate_0031`）在 node（SQLite / MySQL）与 worker（D1）三种形态下均可正确执行
- [ ] 规则 CRUD API 可用，删除/修改后内存缓存即时失效、规则即时生效
- [ ] `scope` 表达式树求值正确：叶子运算符 `=`/`!=`/`in`/`not in`、`{ "type": "const", "values": [true] }` 恒真节点、AND / OR 嵌套组合均正确；空 `and` / `or` 的 `values` 被校验拒绝
- [ ] `vendor_id` 规则在路由选择后正确执行：匹配实际路由到的供应商，不含 `vendor_id` 的规则在路由前执行
- [ ] RPM 限流命中即生效：准入自增计数 + 超限返回 429 + `Retry-After`
- [ ] **供应商级限流 failover**：命中的上游撞限流时切换到下一上游，全部耗尽（或 failover 关闭）时才返回 429
- [ ] 访问控制 deny-if-true 生效：`not in` 白名单、`in` 排除少数均正确，树命中返回 403，且不触发限流计数
- [ ] 命中多条访问控制规则时 fail-closed（任一命中即拒绝）
- [ ] 429 / 403 均写入失败记录（`failed_code` = `rate_limit_exceeded` / `access_denied`）
- [ ] 三协议（OpenAI / Anthropic / Responses）错误体格式正确（429 与 403 均正确）
- [ ] root 用户不受限流与访问控制影响
- [ ] 未配置任何规则时，请求行为与迭代前完全一致（零回归）
- [ ] `/llm/v1/models` 不按访问控制过滤（受限模型仍可见）
- [ ] 前端规则管理页可用（列表 + 增删改，含条件树编辑器、按 type 渲染 config 表单）
- [ ] 后端测试（node 模式）、TypeScript 静态类型检查、前端构建均通过
