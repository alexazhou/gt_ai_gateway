# V1.9: Service / Manager 分层重构 - 技术文档

## 架构概览

V1.9 是纯架构治理迭代，目标层级：

```
controller → service（业务编排） → manager（DAL/持久化） → model（数据模型）
```

- **manager 层（DAL）**：只做数据库读写原语 —— 按主键/唯一键查找、条件查询、列表、计数、创建、更新、删除，不含业务判断。
- **service 层（业务）**：校验、组合、跨实体事务、容错、规则判断，底层 DAL 调用改为调 manager。
- **controller 层**：只保留简单逻辑和调用 service / manager，不再直接碰 `Xxx.query()`。

拆分标准与现状分布、逐 service 拆分清单详见[专项设计](./service_manager_split_design.md)，本文档聚焦落地层面的技术要点。

## 目录结构

新增 `src/manager/` 独立目录，与现有 MVC 惯例（`src/controller/`、`src/service/`、`src/model/`）保持对称，物理隔离防止 manager 反向依赖 service：

```
src/manager/
├── userManager.ts            # findById / findByToken / updateBalance
├── modelManager.ts           # get / list / hasModelsUsingVendor / listEnabled / checkDuplicate / delete / save
├── recordManager.ts          # create / update / latest / clearPayloads + payload io
├── requestActivityManager.ts # findByRecordId / updateActivities / createActivity
├── rechargeRecordManager.ts  # list / get / create
├── vendorManager.ts          # findByName / listAll / findById / update
├── vendorModelManager.ts     # listByVendor / syncByVendor / add / update / delete / getByIds  ← 收编 controller
├── configManager.ts          # get / set / getAll
├── storageManager.ts         # storage_record 表 CRUD（对象存储的 DAL 部分）
└── clientConfigManager.ts    # SgClientConfig 全量 CRUD
```

命名/导入遵循项目规范：默认导出，调用时 `模块名.方法名`。

## 依赖规则

- `service → manager → model`，manager 不反向依赖 service。
- manager 之间尽量不互相调用（避免退化成第二个 service）。
- controller 的裸查询收编后，调用规则如下：
  - **纯 CRUD 接口**（如 `vendorModelController` 的大部分接口）：controller → manager 即可，不经过 service 空壳转发。
  - **涉及业务校验的接口**（如创建前的重复检查）：走 controller → service → manager。
- 不再允许 controller 直接碰 `Xxx.query()` 或 `ormService.dbAdapter`（`statsController` 的 raw SQL 也下沉到 manager）。
- `ormService` / `dbAdapter` 属于基础设施层，不属于 manager/service/controller 任一层，保持现状不动。
- 用 eslint `no-restricted-imports` 约束 manager 不反向依赖 service。

## 逐 service 拆分要点

### 整体搬走（纯 DAL）

- `rechargeRecordService`（40 行）：`listRechargeRecords` / `getRechargeRecord` → `rechargeRecordManager`，整个文件改名。

### 函数级拆分（业务 + DAL 混合）

| Service | 下沉到 manager | 保留在 service |
|---|---|---|
| `requestActivityService` | `findByRecordId` / `updateActivities` / `createActivity` | `append`、`getByRecordId`（JSON 解析容错 + 编排） |
| `modelService` | `getModel` / `listModels` / `hasModelsUsingVendor` / `listEnabledModels` / `checkDuplicateEnabledModel` / `deleteModel` / `filterByVendor` / save | `createModel` / `updateModel`（dup 检查 + validatePrices + validateConfig） |
| `recordService` | `create` / `update` / `latest` / `clearPayloads` / `readPayload` / `writePayload` | `attachPayload`、`recordFailedRequest`、开关判断 |
| `userService` | `getUser` / `findById` / `updateBalance` / `createRechargeRecord` | `getUserByToken`、`adjustBalance` / `deductBalance` / `checkBalance`、`toUnits` / `isRootToken` |
| `vendorService` | `getVendorByName` / `listAll` / find / update | `updateVendor`（proxy 校验 + 序列化）、`findVendorByUrl`、`fetchUpstreamModels` |
| `configService` | `SgConfig` find / create / update / getAll | 缓存 + 默认值逻辑（缓存本身就是它的 manager） |
| `objectStorageService` | `putToTable` / `getFromTable` / `deleteFromTable` / `deleteFromTableByPrefix` | R2 适配、双位置读写编排、位置解析、`normalizeBytes` |
| `clientConfigService/core.ts` | `listByClient` / `findByIdAndClient` / `create` / `update` / `delete` / `disableAllByClient` / `formatUniqueName`（含 `configAdapterUtils` 的 1 处 `.query()`） | 文件系统适配器、`enrichStatus` 比对、`applyConfig` / `createConfig` |
| `routingService/core.ts` | `SgVendor` / `SgVendorModel` 的 find / first / create | 策略选择、候选生成 |

### 无需改动

`senderService`、`responseHandlerService`、`vendorTestService`、`streamLogService`、`updateService`、`cacheService`、`upstreamHealthService`、`pluginService`、`hostService`、`llmRequestService` 无直接 DAL，是纯编排/工具。

## controller 收编规则

现状 ORM 裸查询分布（`SgXxx.query()` / `ormService.dbAdapter.prepare`，不含 HTTP 参数解析）：

| Controller | ORM 裸查询数 | 收编目标 |
|---|---|---|
| vendorModelController | 15 | vendorModelManager（纯 CRUD，controller → manager） |
| vendorController | 7 | vendorManager |
| recordController | 6 | recordManager |
| userController | 6 | userManager |
| systemController | 4 | 对应 manager |
| modelController | 2 | modelManager |
| statsController | 1 ORM + 2 raw SQL | 可下沉部分下沉到 manager；raw SQL 聚合重构与前端联动，另立专项 |

## 事务边界

`adjustBalance`（扣余额 + 写 recharge_record）当前是「两段 DAL 一个业务函数」，拆分后两步写操作分属 `userManager.updateBalance` + `rechargeRecordManager.create`，原子性风险显性化。方案：

- **方案 A（推荐）**：拆分后在 service 层用 sutando 的事务 API 包裹两步调用，确保原子性。
- **方案 B**：两步写在同一个 manager（违反「manager 间不互调」原则，备选）。
- **方案 C**：维持现状不拆此函数的写操作，仅把查询部分（`findById`）下沉到 manager（保守兜底）。

## 迁移策略

采用「先创建 manager + 转发，再逐步修改调用方」的两步走，降低风险：

- **Step 1**：创建 manager，service 中改为调用 manager（service 函数签名不变，manager 函数名与旧 service 保持一致）。
- **Step 2**：确认测试全部通过后，再让 controller 直接调用 manager（跳过 service 空壳）。

第二批涉及的请求热路径依赖链，拆分时须保持函数签名不变，逐条核对：

```
senderService → userService.getUserByToken / checkBalance
responseHandlerService → recordService.attachPayload / userService.deductBalance
responseHandlerService → requestActivityService.append
```

## 测试影响

- `tests/unit/service/` 现有 8 个测试集中在无 DAL 的服务（cacheService、routingService 等），拆分破坏面不大。
- 新增 manager 需补单元测试（建 `tests/unit/manager/` 或对应目录）。
- `query().update()` 是裸 SQL 拼接、不走 casts（vendorService 中已有相关注释），manager 搬移时保持此行为一致。
