# V1.9: Service / Manager 分层重构 - 产品文档

## 目标

当前后端所有业务逻辑集中在 `src/service/` 下，但其中混入了大量「单纯的数据访问层（DAL）」逻辑（按条件查、列表、计数、增删改）；同时部分 DAL 直接散落在 controller 层（如 `vendorModelController` 有 15 处裸查询），绕过了 service 层。

V1.9 的目标是**新增 manager 层，把纯 DAL 逻辑从 service 中剥离，并顺带收编 controller 中的裸查询**，形成清晰的依赖层级：

```
controller → service（业务编排） → manager（DAL/持久化） → model（数据模型）
```

这是一次**纯架构治理**迭代：不改业务行为、不引入新功能，但为后续版本的功能演进提供更稳的底座（分层清晰、边界明确、便于测试与替换存储实现）。

## 功能特性

### manager 层（DAL）落地

- 新增 `src/manager/` 独立目录，按「每个 model 一个 manager」建立 10 个文件：
  - `userManager` / `modelManager` / `recordManager` / `requestActivityManager` / `rechargeRecordManager` / `vendorManager` / `vendorModelManager` / `configManager` / `storageManager` / `clientConfigManager`
- manager 层只做数据库读写原语（查找、条件查询、列表、计数、创建、更新、删除），不含业务判断。

### service 层瘦身

- 把散落在 service 中的纯 DAL 函数下沉到 manager：
  - **整体搬走**：`rechargeRecordService`（100% 纯 DAL，整个文件改名 `rechargeRecordManager`）
  - **函数级拆分**：`requestActivityService`、`modelService`、`recordService`、`userService`、`vendorService`、`configService`、`objectStorageService`、`clientConfigService/core.ts`、`routingService/core.ts`
- service 保留并聚焦业务逻辑：校验、组合、跨实体事务、容错、规则判断。

### controller 裸查询收编

- `vendorModelController`（15 处）、`vendorController`（7 处）、`recordController`（6 处）、`userController`（6 处）、`systemController`（4 处）、`modelController`（2 处）的 ORM 裸查询全部收编到 manager。
- 收编后的调用规则：
  - **纯 CRUD 接口**：controller → manager，不经过 service 空壳转发。
  - **涉及业务校验的接口**：controller → service → manager。
- 重构后不再允许 controller 直接碰 `Xxx.query()` 或 `ormService.dbAdapter`。

### 事务原子性保障

- `adjustBalance`（扣余额 + 写 recharge_record）拆分到不同 manager 后，原子性风险显性化：
  - **方案 A（推荐）**：service 层用 sutando 事务 API 包裹两步调用。
  - **方案 B**：两步写在同一个 manager（违反「manager 间不互调」原则，备选）。
  - **方案 C**：维持现状不拆写操作，仅查询部分下沉（保守兜底）。

### 依赖治理

- 采用 eslint `no-restricted-imports` 约束 manager 不反向依赖 service，物理 + 规则双重隔离。

## 产品边界（非目标）

- **不改业务行为**：不改变任何对外接口、请求链路、计费结果。
- **不引入新功能**：不新增对外能力，纯内部重构。
- **statsController 的 raw SQL 重构不在本版本范围**：与前端联动、需另立专项，本版本仅下沉可独立的部分。
- `ormService` / `dbAdapter` 属于基础设施层，不属于 manager/service/controller 任一层，保持现状不动。

## 验收标准

- [ ] `src/manager/` 目录建立，10 个 manager 建齐，命名/导入遵循项目规范（默认导出、`模块名.方法名`）
- [ ] `vendorModelController` 15 处裸查询全部收编，重构后 controller 无 `SgXxx.query()` 直接调用
- [ ] 热路径依赖链（`senderService` / `responseHandlerService` 相关调用）函数签名不变
- [ ] `adjustBalance` 两步写操作的事务原子性有明确保障
- [ ] 行为零回归：各协议请求、计费、路由行为与重构前一致
- [ ] 全量后端测试（node + worker 模式）、TypeScript 静态类型检查、前端构建均通过
